# Проверятор

Nuxt/Vuetify приложение со статической сборкой. Все запросы и обработка камеры выполняются в браузере; серверных плагинов и Nuxt API routes нет.

## Запуск и сборка

```sh
npm install
npm run dev
npm run typecheck
npm test
npm run build
```

Размещайте содержимое `.output/public`. Для каждого экрана генерируется фиксированная страница; идентификаторы находятся в query:

- `/works/view?id=...&kind=draft` или `kind=version`
- `/works/new?id=...` — редактирование; без ID — создание
- `/works/check` — отдельное сканирование без обязательного ID задания
- `/works/results?scanId=...` — результаты сессии; старые ссылки с `batchId` также поддерживаются
- `/works/results` — все сохранённые проверки текущего учителя; `taskId` открывает выбранную работу.

Параметры из `.env.example` задаются **до сборки**. Они включаются в клиентскую статику. В них нельзя помещать секреты.

## Реальные сервисы

- `NUXT_PUBLIC_API_BASE`: адрес Go backend. Редактор использует авторизованный `/api/v1/constructor/*`: импорт, разбор, предпросмотр, черновики и версии. Вход — `/api/v1/auth/login`. Типы backend берутся из `app/types/backend.d.ts` через отдельные глобальные aliases.

Нужна интеграция конструктора из backend `origin/slop`, коммит `101c1f4` (`feat: integrate test constructor, persistent gradebook and analytics`), OpenAPI 0.4.0. На момент подключения в `main` (`4a32261`) её нет. Самостоятельные `/api/import` и `/api/capabilities` относятся к локальному прототипу и фронтендом не вызываются. Контракт скопирован из указанного Git ref, `backend.d.ts` заново сгенерирован openapi-typescript 7.13.0.

Все `/api/v1/*` направляются в Go. Go проверяет teacher-сессию и вызывает внутренний Test Studio через `TEST_STUDIO_URL` и серверный `TEST_STUDIO_SERVICE_TOKEN`; токен в браузер не передаётся. Для разных origin настройте CORS и credential requests backend. Для API на том же origin `API_BASE` может быть пустым.

Создание начинается с темы и одного файла. После распознавания показываются условия и по одному полю ответа к каждому заданию. Сохранение ключа подтверждает введённые ответы. Настройки печати, технические параметры OCR, JSON и модальное окно разбора в интерфейсе не показываются. У нераспределённых рисунков можно выбрать соответствующее задание.

## Авторизация и хранение

Backend использует HttpOnly cookie `teacher_session`: вход, `GET /api/v1/auth/me`, выход. Bearer token и refresh-token API не используются. HTTP-регистрации и восстановления пароля в текущем контракте нет.

Каталог загружается с сервера: `/api/v1/constructor/drafts` и `/versions`. Черновик сохраняется с `request_id` и `expected_revision`, а публикация фиксирует его ревизию и получает неизменяемый PDF из S3. Готовый ключ не требуется для сканирования: backend solver строит ответы по отправленным фотографиям. Идентификаторы заданий сопоставляются по `layout_task_id`, числовому `errorlab_task_id` и порядку печати; ответы и темы в конструкторе учитель задаёт явно. Старое локальное IndexedDB-хранилище предыдущей реализации автоматически не удаляется и не публикуется.

В списке показаны готовые ключи и изменённые черновики; сканирование не меняет статус ключа. Проверки живут отдельно. Их контекст, фото, cursor и результаты сохраняются в IndexedDB `proveryator-scanner-captures`. Продолжение проверки требует того же браузера: контракт пока не содержит endpoint получения полной метаинформации batch.

## Сканер

`app/scanner/vision` и `ScanController` перенесены из `subfrontends/scanner` без изменения распознавания, геометрии, порогов качества и физического цикла листа. Предпросмотр сохраняет contain, зеркалирование и координаты обводки; на сервер идёт канонически ориентированный кадр.

Каждая новая фотография сразу отправляется как отдельная работа: исходный Blob → один batch с variant=auto и одним листом → закрытие batch → проверка. ФИО, каталог ключей, OCR подготовки и объединение страниц в этом потоке не используются. Идентификаторы фотографии и страницы сохраняются до отправки. Новое сканирование создаёт свежую сессию; старые неотправленные фото сохраняются в браузере и автоматически не повторяются. «Завершить» ждёт текущую очередь и открывает результаты.

Результаты сопоставляются по task ID. Cursor и данные фиксируются до ACK. ACK доступен только после полного завершения, а ученики без листов требуют отдельного подтверждения. ACK разрешает backend очистить временные данные; фото и результаты в браузере автоматически не удаляются.

На странице «Мои работы» есть отдельная таблица проверенных работ с переходом к фото и ошибкам. Результаты незавершённых проверок запрашиваются каждые 2,5 секунды через `GET /api/v1/batches/{batchId}/results`: этот backend endpoint читает Redis cache с PostgreSQL fallback. Завершённые сессии восстанавливаются из IndexedDB, включая после обновления страницы. Другие пользователи не видят локальные проверки текущего учителя.

Просмотр показывает исходные фотографии, отправленные в backend, с переключением листов и пронумерованными областями ошибок из `result.boxes`. Координаты 0–1000 масштабируются вместе с фото; `result.pages[].page_id` связывает разметку с точным листом. Нажатие на рамку открывает пояснение AI. Если координат нет, фронтенд не рисует вымышленных рамок. Для получения рамок AI worker должен вызывать `find_boxes` до перевода диагностических статусов в `manual`; исправление находится в backend `ai-service/errorlab/worker.py`. Фото остаются доступными в браузере, в котором сканировали; автоматического ACK нет.

Тесты используют синтетические HTTP ответы и реальный reference raster; производственный клиент заглушек не содержит. Тесты не подтверждают работу конкретной камеры и освещения.
